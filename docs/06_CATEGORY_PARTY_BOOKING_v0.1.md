# SlotMate 확장 설계 v0.1 — 카테고리 · 여러 명 예약 (1단계)

- 작성일: 2026-10-21 · 상태: 확정 (결정 A·B 2026-10-21 추천안으로 확정)
- 방향: 헬스장 전용 → **카테고리별 상품 + 공통 예약·대기 엔진**. 운동 · 원데이클래스 · 놀거리
- 2단계(별도 설계): 숙박 — 여러 박 재고를 한 번에 잡는 모델이라 회차 엔진과 다름

## 1. 범위

| 넣음 | 뺌 (1단계) |
|---|---|
| 카테고리 3개와 세부 종류 | 숙박 |

| 자리 수 기준 정원·대기·승격 | 최소 인원·자동 취소, 환불 규정 |
| 카테고리 필터 화면, 인원 선택 화면 | 호스트별 계정·권한 분리 |
| 데모 데이터: 원데이클래스·놀거리 상품 | 예약 후 인원 변경 (취소 후 다시 예약) |

## 2. 카테고리

카테고리는 별도 컬럼 없이 **세부 종류(program_type)가 속한 카테고리**로 정함 — 종류와 카테고리가 어긋날 수 없음

| 카테고리 | 세부 종류 (program_type) | 재고 |
|---|---|---|
| 운동 `EXERCISE` | PT · 요가 · GX · 필라테스 · 기타 운동 (기존 그대로) | 시간 회차 |
| 원데이클래스 `CLASS` | 공예 `CRAFT` · 요리 `COOKING` · 미술 `ART` · 기타 클래스 `CLASS_ETC` | 시간 회차 |
| 놀거리 `ACTIVITY` | 투어 `TOUR` · 체험 `EXPERIENCE` · 레저 `LEISURE` | 시간 회차 · 하루짜리 회차(입장권형) |

- 기존 `ETC` 는 운동 카테고리의 「기타 운동」으로 둠 → 기존 데이터 이전 없음
- 조회 API 에 `category` 필터 추가. 기존 `type` 필터는 그대로

## 3. 여러 명 예약

### 3.1 데이터

| 테이블 | 추가 컬럼 | 규칙 |
|---|---|---|
| `programs` | `max_party_size SMALLINT NOT NULL DEFAULT 1` | 예약 1건 최대 인원 (결정 B) |
| `reservations` | `party_size INT NOT NULL DEFAULT 1` | 1 이상, 프로그램 `max_party_size` 이하, 회차 정원 이하 |

- 정원은 **자리 수**. 확정 자리 = `SUM(party_size) WHERE CONFIRMED`
- 잔여석 = 정원 − 확정 자리. 화면의 「예약 8/10」은 자리 기준
- 같은 회원·같은 회차 활성 예약 1건 규칙은 그대로 (일행은 대표 1명이 인원으로 예약)

### 3.2 신청

1. 회차 행 잠금 (지금과 같음)
2. 인원 검증: 1 ≤ 인원 ≤ `max_party_size`, 인원 ≤ 정원 → 아니면 400 `INVALID_PARTY_SIZE`
3. 확정 자리 + 인원 ≤ 정원 → `CONFIRMED`, 아니면 팀 전체 `WAITING` (팀을 쪼개지 않음)

### 3.3 취소 → 승격 (결정 A)

**들어갈 수 있는 팀 먼저 (first-fit)**

1. 확정 취소로 빈 자리 k 개
2. 대기 팀을 오래 기다린 순(`requested_at`, `reservation_id`)으로 보면서 인원 ≤ 남은 자리인 팀을 승격, 남은 자리에서 뺌
3. 남은 자리가 0 이거나 들어갈 팀이 없을 때까지 반복 — 한 번의 취소로 여러 팀이 승격될 수 있음

| 예 | 자리 2 · 대기 A 3명 → B 2명 → C 1명 |
|---|---|
| 추천안 | A 건너뜀 → B 승격 → 끝. 빈자리 0, A 는 대기 1번 유지 |
| 대안 (순서 엄수) | A 가 안 들어가므로 멈춤. 빈자리 2, 아무도 승격 안 됨 |

- 추천 이유: 빈자리가 남지 않음(호스트 손실 없음). 1명 예약만 있는 운동 수업은 지금과 결과가 같음
- 대가: 큰 팀이 작은 팀에 계속 밀릴 수 있음 → 대기 화면에 「앞 팀 수」와 함께 「필요 자리」 표시
- 신청과의 일관성: 승격이 끝난 뒤 남은 자리는 「대기 중인 어떤 팀도 못 들어가는 자리」 → 새 신청이 그 자리에 들어가도 순서 위반 아님

### 3.4 대기 순번

- 순번 = 같은 회차에서 나보다 먼저 기다린 **팀 수** + 1 (지금 계산 그대로)
- 응답에 `partySize` 추가. 화면: 「대기 2번째 · 3명」

### 3.5 동시성

- 잠금 구조는 그대로: 신청·취소 모두 회차 행 잠금 후 처리, 취소의 잠금 뒤 조회는 잠금 조회
- 승격 반복은 같은 트랜잭션 안에서 대기 목록을 잠금 조회로 한 번 읽고 순서대로 처리
- 검증: 동시 신청(인원 섞임)에서 확정 자리 합 ≤ 정원, 동시 취소에서 승격 순서 규칙 위반 0 — JUnit + k6 시나리오 추가

## 4. API 변경

| API | 변경 |
|---|---|
| `POST /sessions/{id}/reservations` | 본문 `{ "partySize": 3 }` (생략하면 1) |
| `GET /sessions`, `GET /programs` | 쿼리 `category`, 응답 `category`·`maxPartySize` 추가 |
| 예약 응답 (7.1 · 7.2 · 9.5) | `partySize` 추가 |
| 관리자 프로그램 등록·수정 | `maxPartySize` (기본 1) |
| 오류 | 400 `INVALID_PARTY_SIZE` |

- 기존 클라이언트(본문 없이 신청)는 1명 예약으로 그대로 동작

## 5. 화면 변경

| 화면 | 변경 |
|---|---|
| 회원 홈 | 날짜 줄 아래 카테고리 탭(전체 · 운동 · 원데이클래스 · 놀거리), 그 아래 세부 종류 칩 |
| 수업 카드·상세 | `maxPartySize > 1` 이면 인원 선택(−/+) 후 예약. 잔여석보다 많으면 「대기 신청」 버튼으로 바뀜 |
| 내 예약·알림 | 인원 표시 「3명」 |
| 관리자 | 프로그램 폼에 카테고리·종류·최대 인원, 회차별 예약자에 인원 열 |

## 6. DB 변경 적용

- `db/init/01_schema.sql` 에 컬럼 추가, 기존 DB 는 `db/changes/2026-10-xx_party_size.sql` (ALTER 2개, 기본값 1 이라 기존 데이터 그대로)
